# 信息板图片加载卡顿治理方案

日期：2026-05-09

关联项目：`/Users/kehongli/studio/openworld-js/open-world-zone`

关联插件：

- `open-world-zone/plugins/signboard_lab`
- `open-world-zone/plugins/tab`

本文件记录这次围绕“信息板图片多时漫步卡顿”的思考、需求确认、代码方案、阶段性建议和后续复盘要点。它不是单纯的代码变更说明，而是给后续继续优化时看的工作笔记。写得细一点，是因为这个问题的本质不是某一行代码慢，而是浏览器图片加载、主线程解码、WebGL 纹理上传、动态区块激活、业务懒加载这几件事叠在同一个瞬间，形成了体感上非常不舒服的一下卡顿。

## 1. 需求确认结果

这次用户明确给出了 8 个关键判断，这些判断直接决定优化方向。

第一，目标不是“图片必须瞬间出现”，而是“相机移动必须丝滑”。这点很重要。传统页面优化经常追求首屏快、图片尽快显示，但在 3D 漫游里，操控连续性比内容瞬时完整更重要。图片可以晚一点出现，甚至可以先显示 Loading 或低清占位，只要玩家转头、前进、后退时不要被突然冻结一下。也就是说，优化优先级是：交互连续性 > 帧尖峰降低 > 图片出现速度 > 图片首次显示质量。

第二，代码修改范围被限制在 `open-world-zone` 目录下，不能动 `/Users/kehongli/studio/openworld-js/src`。这意味着不能直接改 WebGL 核心 `W.setState()`，不能直接改 `src/wjs/w.js` 里的 `texImage2D` 和 `generateMipmap`，也不能直接改 `src/obj/chunkManager.js` 的区块激活算法。这个限制会让优化方案更偏“外层调度”和“业务队列”，也就是在调用核心引擎之前，把重活拆开，避免同一帧塞太多任务。

第三，服务端已经废弃，不作为本阶段优化对象。`signboard_lab/server` 不用改，也不依赖服务端新增缩略图接口、分页接口、图片代理接口或 CDN 转码接口。所有第一阶段方案都必须在前端侧闭环。这个限制会让“服务端生成缩略图”暂时不可用，但仍然可以在客户端做大图缩放、延迟上传和持久缓存。

第四，图片可以延迟出现，可以先用占位内容。这给了足够空间做渐进式加载。当前代码里 image 模式之前有一行被注释的 `drawSmartText(ctx, width, height, 'Loading...')`，这次恢复它的意义不是为了好看，而是为了让图片任务可以排队。先让信息板有一个轻量占位纹理，真正图片由队列慢慢替换。

第五，加载顺序按信息板原始顺序，不按距离、不按视线方向。这个选择让方案更稳定、可预测，也更容易复盘。距离和视线优先级以后可以做，但它会引入更多状态判断，比如玩家转身后优先级变化、队列重排、旧任务取消等。第一阶段先按触发顺序 FIFO，可以最大限度减少变量。

第六，内存策略倾向长期保留。已经加载过的图片不需要离开视野就释放，目标是下次回来不卡。这个判断会影响缓存设计：我们不主动清理 `textureMap`、隐藏 `img`、已创建的 WebGL texture。短期内这会换取更好的二次访问体验。代价是长时间漫游后内存可能上涨，后续可以加上软上限和调试面板，但第一阶段不做强回收。

第七，同一区域可能同时存在 80 张左右信息板，其中一部分已经在内存里。80 张是一个很关键的量级。单张图片上传也许只是 5 到 20ms，但 80 张挤在一起就会形成秒级级联卡顿。更现实的是，不是每张都一样大，有些可能是普通 JPG，有些可能是很大的 PNG，有些可能是 SVG 或外链图。优化不能假设图片都很轻。

第八，调试措施必须先搞好。这个要求非常对。过去这类问题容易陷入“我感觉更顺了”或者“某次测试不卡了”的陷阱，但没有数据就不知道到底是 fetch 慢、decode 慢、canvas 缩放慢、WebGL 上传慢，还是批量 `updateSign` 引发的同步重建慢。第一阶段必须把队列长度、上传耗时、帧尖峰、最后几个事件都暴露出来，后续再基于数字调参数。

## 2. 当前代码里的卡顿链路

这次深挖后，比较明确的链路如下。

玩家走到一个信息板密集区域时，动态区块系统会根据玩家所在格子决定哪些物体进入激活集合。核心逻辑在 `src/obj/chunkManager.js`，但本阶段不能改它。它会在同一次动态节点计算里调用多个对象的 `activeTABox()`。信息板是通过 `dataProc.process()` 写入档案的 plane，对应材质纹理通常是一个字符串 ID。

当 `activeTABox()` 发现纹理字符串在 `textureMap` 和 `window` 上都找不到时，会走错误纹理生成路径：调用 `loadTexture()`，再触发 `errorTexture_diy` hook。`signboard_lab/signTest.js` 就是挂在这个 hook 上做业务判断：如果 `signContentMap` 里已经有数据，就绘制文本或处理图片；如果没有数据，就调用 `lazyLoadSign(id)` 去服务器批量获取。

`store.js` 当前有 100ms 合并请求逻辑，这本身是合理的，避免一个板子一个请求。但是请求回来后，旧逻辑会直接遍历 `data.boards`，对每一个 board 立刻调用 `window.updateSign(board.id, ...)`。`updateSign` 会改 `indexToArgs` 里的 `texture`，清理部分 `textureMap`，并把 `currentlyActiveIndices` 里对应 index 删除。这样下一次动态激活时，这些对象会重新进 `activeTABox()`，再次触发 hook。

如果返回的 80 个 board 里很多是 image 模式，旧逻辑会很快创建大量隐藏 `<img>`，并让浏览器同时开始加载这些外链图片。图片 onload 后，旧 `imageHandler.js` 会立刻调用 `applyImage()`，里面直接 `ccgxkObj.W.plane({ n:'T'+index, t: imgEl, ... })`。虽然 `W.plane` 看起来是业务层调用，但核心 `W.setState()` 会发现 `state.t.width` 存在，并且 `W.textures[state.t.id]` 不存在，于是同步执行 `gl.createTexture()`、`gl.texImage2D()`、`gl.generateMipmap()`。这一步是非常典型的主线程和 GPU 同步热点，尤其是大图或多图连续上传时，很容易出现“不是一直低 FPS，而是突然定住一下”的体感。

所以卡顿不是单一 fetch 导致，也不是单一图片 DOM 导致，而是多个阶段没有节流：批量数据返回没有节流，图片网络/解码没有节流，纹理上传没有节流，旧图片完成时也没有检查玩家是否已经离开。它们一旦在同一段时间汇合，就会造成突发尖峰。

## 3. 第一阶段策略

在不能动 `src` 的前提下，第一阶段采用“外层削峰”的策略。核心思想是：不试图让单张图片上传变成零成本，而是确保每一帧附近最多只有一个重任务，且这些重任务之间有足够间隔。

第一层是 `updateSign` FIFO 队列。服务器批量返回后，`store.js` 仍然马上把数据写入 `signContentMap`，这样面板、HotInfo 和本地状态不会丢。但是不再直接循环调用 `window.updateSign`。新的 `updateQueue.js` 会按原始触发顺序把 board 放入队列，默认每隔约 60ms 放行一个。这样做可以避免 80 个 board 同一帧全部被标记为重新激活，也减少同一时间进入 image hook 的数量。

第二层是图片加载 FIFO 队列。`handlers/imageHandler.js` 不再在 `handleImageMode()` 里立即创建图片并开始加载，而是先进入 `loadQueue`。默认 `maxActiveLoads = 1`，也就是严格一张一张加载和 decode。这个值看起来保守，但它符合当前目标：图片可以慢慢出现，走路不能卡。后续如果确认 decode 和网络不是主要问题，可以临时调成 2 或 3。

第三层是纹理上传 FIFO 队列。即使图片已经 onload，也不会立刻 `W.plane`。它会进入 `uploadQueue`，默认两次上传之间至少间隔 120ms。真正调用 `W.plane` 的时候会记录耗时，这个耗时基本覆盖业务层调用到 WebGL 上传链路的尖峰。这样即使一张图上传本身仍有 20ms 峰值，也不会 80 张连续把浏览器锁住。

第四层是大图缩放。因为不能改 `W.setState()`，所以只能在传给 W 之前把图片变成更温和的纹理源。当前默认 `maxTextureEdge = 1024`。如果原图最大边超过 1024，会先画到一个 canvas，再把 canvas 作为纹理传给 `W.plane`。plane 的宽高比仍然使用原图尺寸，不使用压缩后的 canvas 尺寸，所以视觉比例不会变。这个方案牺牲一部分远看不太需要的像素细节，换取更小的 GPU 上传体积和 mipmap 成本。

第五层是旧任务跳过。图片加载是异步的，玩家可能已经走远，或者同一块板子已经被更新成另一个 random 纹理 ID。如果图片晚到后仍然贴图，就可能出现旧图突然贴回场景，也会浪费上传。新逻辑在上传前检查：当前 index 是否仍在 `currentlyActiveIndices`，且 `indexToArgs.get(index).texture` 是否仍等于任务 id。不满足就跳过上传，只保留已经加载好的 DOM 图片，等下次真的需要再进队列。

## 4. 新增诊断体系

新增 `signboard_lab/diagnostics.js` 作为统一诊断中心。它会记录以下信息：

- rAF 帧间隔，包含 last delta、max delta、超过阈值的 hitch 次数、最近一次 hitch 的时间和 delta。
- update 队列，包含 queued、applied、failed、pending、maxPending、最近一次 boardId、最近一次 apply 耗时。
- image 队列，包含 queued、cacheHits、loadStarted、loadFinished、decodeFinished、uploadQueued、uploaded、failed、skippedInactive。
- 图片阶段耗时，包含 load、decode、downscale、upload 的 last 和 max。
- 最近事件流水，只保留最近一小段，避免长期运行撑内存。

全局调试入口如下：

```js
window.signboardPerf.snapshot()
window.signboardImageQueue.snapshot()
window.signboardUpdateQueue.snapshot()
```

其中 `window.signboardPerf.snapshot()` 是最主要的快照。它可以直接在控制台执行，也可以通过 Tab 面板的 Dump Console 按钮打印。`window.signboardImageQueue.setConfig()` 可以临时调参数，例如：

```js
window.signboardImageQueue.setConfig({
  uploadIntervalMs: 200,
  maxTextureEdge: 768,
  maxActiveLoads: 1
})
```

这几个参数不写入持久配置，目的是让现场测试可以快速试错。比如如果 upload max 仍然很高，可以把 `maxTextureEdge` 从 1024 调到 768；如果图片出现太慢但上传耗时很低，可以把 `uploadIntervalMs` 从 120 调到 80；如果网络加载很慢但 decode/upload 不高，可以把 `maxActiveLoads` 调到 2。

Tab 插件新增 `Signboard Diagnostics` 区域。它显示 frame、hitches、updates、loads、uploads、upload ms、decode ms、downscale、skipped、next、config 等摘要。这个面板的定位不是漂亮 UI，而是“边走边看”。当你走进 80 张信息板区域时，可以观察 pending 是否堆积、uploaded 是否稳定增长、hitch 是否仍然集中出现。如果卡顿仍在，但 upload max 不高，就说明问题可能还在 placeholder 生成或区块激活本身；如果 upload max 特别高，下一阶段就继续压纹理尺寸或延后上传。

## 5. 当前代码改动要点

新增 `open-world-zone/plugins/signboard_lab/diagnostics.js`。这个文件负责指标聚合、事件记录、帧尖峰监控和全局快照。它不直接改变业务行为，所以即使后续策略改掉，诊断中心也可以继续保留。

新增 `open-world-zone/plugins/signboard_lab/updateQueue.js`。这个文件负责批量懒加载返回后的 `window.updateSign` 节流。`store.js` 会在请求成功后按 ids 原始触发顺序重排返回 boards，再逐个 `enqueueSignboardUpdate()`。这点很关键，因为服务端 SQL 的 `IN` 查询不一定保证顺序，前端必须根据 pending ids 自己恢复 FIFO。

修改 `open-world-zone/plugins/signboard_lab/store.js`。批量返回不再直接循环 `window.updateSign`，而是进入 update queue。未找到内容的 empty/text 调试更新也进入队列，避免空板子也瞬间触发大量重建。

重写 `open-world-zone/plugins/signboard_lab/handlers/imageHandler.js` 的加载策略。它现在有 `loadQueue` 和 `uploadQueue`。`handleImageMode()` 只负责把任务塞进队列。真正图片请求由 `startNextLoad()` 控制，真正贴图由 `processUpload()` 控制。它还会复用 `textureMap` 或隐藏 DOM img 缓存，大图会压成 canvas 纹理，SVG naturalWidth 为 0 时仍保留 fetch fallback。

修改 `open-world-zone/plugins/signboard_lab/signTest.js`。image 模式恢复 Loading 占位绘制，并在插件入口启动 `signboardPerf.startFrameMonitor()`。Loading 占位的价值是让用户看到板子处于等待状态，同时给真实图片排队争取时间。

新增 `open-world-zone/plugins/tab/signboardPerfPanel.js`，并修改 `tab.js` 引入它。Tab 面板增加 Signboard Diagnostics 区域，提供 Reset Stats 和 Dump Console。因为用户明确说 tab 插件可以改，而且调试措施必须先搞好，所以把诊断入口放在 Tab 里是合理的。

同步更新 `open-world-zone/plugins/signboard_lab/claude.md`。新增文件、关键策略、控制台入口、更新日志都记录进去，避免后续回看插件结构时漏掉这次队列化机制。

## 6. 为什么不直接追求最快显示

这个问题里很容易走偏：看到图片慢，就想增加并发；看到队列长，就想一次多处理几张；看到有 80 张，就想预取。但这次用户的核心痛点不是“图没出来”，而是“人走路时突然卡一下”。所以第一阶段宁愿保守。

浏览器对图片的处理有几个不可控点。fetch 可以异步，但图片 decode 不一定完全不影响主线程；canvas drawImage 可能有成本；WebGL `texImage2D` 在多数场景下是同步触发上传；`generateMipmap` 对大图也可能很重。更麻烦的是，这些成本不是平均分布，而是某个资源准备好后集中爆发。80 张图同时准备好时，任何一个阶段都会形成峰值。

FIFO 队列化的目标不是减少总工作量，而是改变工作量的时间分布。总耗时可能变长，但体感会更稳。真实漫游里，人不会在 1 秒内读完 80 张图，图片逐张出现是可接受的；但相机冻结 300ms 就非常难受。这就是为什么第一阶段默认 `maxActiveLoads = 1` 和 `uploadIntervalMs = 120`。它们不是最终值，而是先把尖峰压下来，之后用诊断数据再提速。

## 7. 后续可选优化方向

第一阶段完成后，后续可以按数据继续推进。

如果 Tab 面板显示 upload max 仍然很高，说明单张图片上传仍然太重。可以继续降低 `maxTextureEdge` 到 768 或 512，也可以做按信息板物理尺寸决定纹理尺寸，而不是统一 1024。比如小板子根本不需要 1024，大板子才需要更高。这个策略不需要动 `src`，可以在 `imageHandler.js` 根据 `canvasH` 和距离估算。

如果显示 update 队列 apply 耗时很低，但 image queue 堆积太慢，可以提高 `maxActiveLoads` 到 2。需要观察 decode max 和 frame hitch 是否变差。如果不变，可以保留 2；如果变差，说明 decode 或浏览器图片管线仍有冲击。

如果显示 skippedInactive 很多，说明玩家移动速度超过图片显示速度，很多图加载完时已经不在视野附近。此时可以考虑在加载前加“仍在附近”的检查，甚至在 loadQueue 阶段跳过已经离开的任务。但这会和“按原始顺序”有一点冲突，需要用户确认是否允许跳过离开的板子。

如果二次进入仍然卡，说明 DOM 图片缓存和 textureMap 还不够，可能是 W 层 `W.textures` 的 key 与业务 id 的关系导致重新上传，或者 canvas 纹理没有被充分复用。因为不能动 `src`，可以在业务层保证同一 id 始终复用同一个 `textureSource.id`。当前 canvas 使用 `id` 作为 texture key，普通 img 使用隐藏 DOM img 的 id，后续可以进一步统一。

如果长期内存过高，可以加软上限，但第一阶段不主动回收。软上限可以只清理最老的 DOM img 和 textureMap，不清 W.textures，因为 W.textures 没有公开删除流程。更完整的释放需要动 `src/wjs/w.js`，当前约束下先不做。

如果想更激进，可以做 IndexedDB 缓存，把外链图片第一次加载后转 blob 缓存起来。这样下次进入页面也快。但这会带来跨域、存储配额、失效策略、URL 版本判断等问题，不适合第一阶段。

如果服务端未来重新启用，最佳方案是服务端或边缘侧生成多档缩略图。前端先加载 512 或 1024 纹理，用户点“查看原图”时再打开原图。这样比浏览器端 drawImage 更省本机 CPU。但这次服务端废弃，所以只作为未来方向记录。

## 8. 现场复盘方法

建议测试时按以下流程看数据。

第一步，刷新页面后打开 Tab 面板，找到 Signboard Diagnostics，点 Reset Stats。这样前面的初始化帧尖峰不会污染数据。

第二步，走向已知有大量信息板的区域。观察 Frame 的 max 和 Hitches。只要相机没有明显冻结，但 hitches 数字有增加，可以接受；如果 maxDelta 仍然出现 200ms 以上，就要继续看 Upload ms 和 Downscale ms。

第三步，看 Updates。正常情况下 queued 会随着批量返回增加，applied 会按 60ms 左右一个慢慢追上。pending 如果长时间不动，说明队列卡住；如果 applied 很快追上但图片仍没出来，要看 image queue。

第四步，看 Loads 和 Uploads。Loads 代表图片加载和 decode 完成数量，Uploads 代表真正贴进 WebGL 的数量。waitingUploads 如果快速堆高，说明网络加载比上传快，上传是瓶颈。waitingLoads 如果堆高但 activeLoads 始终 1，这是预期，因为第一阶段严格 FIFO。

第五步，看 Upload ms。这个值最接近以前“突然卡一下”的核心。如果 last 或 max 经常大于 30ms，说明单张图仍然偏重。可以临时在控制台执行：

```js
window.signboardImageQueue.setConfig({ maxTextureEdge: 768, uploadIntervalMs: 160 })
```

然后 Reset Stats 再走一次，看 maxUploadMs 和 frame hitch 是否下降。

第六步，点 Dump Console，把三份快照打印出来。后续复盘时可以把控制台内容贴出来，对比不同参数下的队列和耗时。

## 9. 风险和注意事项

第一，图片出现会比以前慢。这是主动选择，不是 bug。当前目标是相机移动顺滑。如果用户后续觉得太慢，可以用诊断数据逐步放宽参数，而不是直接恢复并发。

第二，Loading 占位也会生成纹理。它比真实图片轻很多，但不是零成本。如果未来发现刚进入区域时即使没有真实图片也卡，下一步要继续优化占位纹理生成，比如复用统一 Loading 纹理，或让 image 模式在首轮 hook 中先隐藏、不生成每块独立 Loading canvas。

第三，当前不释放长期缓存。长时间漫游后内存上涨是预期代价。因为用户明确选择“长期留在内存”，第一阶段不做 LRU。后续如果内存压力明显，再加统计和软回收。

第四，SVG fallback 仍然需要 fetch 原始 SVG 文本。如果某些 SVG 跨域策略不允许 fetch，但 img 标签可加载，可能仍会失败。这是旧逻辑也存在的问题。后续可以把 SVG 失败也降级为普通占位，不阻塞队列。

第五，`texImage2D + generateMipmap` 仍然在 `src/wjs/w.js` 内部同步执行。因为本阶段不能动 `src`，只能通过队列和缩放减少它的集中程度。如果未来允许动核心，应该考虑禁用部分 mipmap、改纹理参数、复用 texture、显式删除 texture，以及把上传策略做进 W 层。

第六，`currentlyActiveIndices` 检查能避免旧图贴回，但它也意味着玩家移动很快时，已经加载好的图可能暂时不上传。下次回到附近会复用 DOM img 重新排队上传。这符合“移动优先”的目标。

## 10. 当前阶段结论

这次优化的第一性判断是：卡顿来自“重任务集中”，不是来自“总任务存在”。只要世界里有 80 张图片信息板，加载、decode、上传这些工作总要发生。真正要避免的是它们在玩家刚走进某个区域时同一瞬间发生。

因此第一阶段不是追求最聪明的预取，也不是追求最复杂的优先级，而是先建立可观测性，然后做最稳的削峰：批量更新削峰、图片加载削峰、纹理上传削峰、大图上传体积削峰、旧任务上传削峰。这个方案保守，但符合当前约束和目标。

后续复盘时，优先看数据，不要靠感觉调整。若 frame hitch 明显下降而图片出现慢，就放宽队列；若图片出现快但 hitch 又回来，就收紧队列或降低纹理尺寸。调参应该围绕 `maxTextureEdge`、`uploadIntervalMs`、`maxActiveLoads` 三个旋钮展开。只要这三个数字和 Tab 面板的指标一起记录，后续每一次优化都能留下可比较的证据。
